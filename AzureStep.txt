ExamVault — Azure Dev Environment: Step-by-Step Runbook
=========================================================
This is a reproducible, step-by-step record of how the "dev" Azure
environment was built, in the order it actually happened, plus the current
status and open issues. Written so the same steps can be re-run (for qa/prod
later) or re-applied if the dev environment ever needs rebuilding.

Prerequisites (already true on this machine)
----------------------------------------------
- Azure CLI installed and logged in: `az login`, `az account show` confirms
  the right subscription is active.
- Docker Desktop installed and running (used for local image builds - see
  Step 6, the CD pipeline route hit an unresolved problem).
- Bicep CLI available (`az bicep install` if not).

STEP 1 — Register required Azure resource providers
------------------------------------------------------
One-time per subscription. All were `NotRegistered` initially.
    az provider register -n Microsoft.App
    az provider register -n Microsoft.ServiceBus
    az provider register -n Microsoft.Sql
    az provider register -n Microsoft.ContainerRegistry
    az provider register -n Microsoft.OperationalInsights
Check status with: az provider show -n <name> --query registrationState -o tsv

STEP 2 — Deploy the shared Azure Container Registry
--------------------------------------------------------
One registry, shared across dev/qa/prod (not per-environment). Lives in its
own resource group so its lifecycle is independent of any single
environment.
    az group create --name rg-examvault-shared --location centralindia
    az deployment group create \
      --resource-group rg-examvault-shared \
      --template-file Infra/shared.bicep

Result: acrexamvaultshared.azurecr.io

STEP 3 — Deploy the dev environment infrastructure (Bicep)
----------------------------------------------------------------
Template: Infra/env.bicep (see Infra/README.md for full parameter list and
design notes). Provisions: Log Analytics, Container Apps Environment, Azure
SQL server + Basic elastic pool (5 databases), Service Bus namespace
(Standard tier), and 10 Container Apps bootstrapped on a public placeholder
image with no registry wired yet.

    az group create --name rg-examvault-dev --location centralindia

    az deployment group what-if \
      --resource-group rg-examvault-dev \
      --template-file Infra/env.bicep \
      --parameters environmentName=dev sharedResourceGroupName=rg-examvault-shared \
      --parameters sqlAdminPassword=<generate-strong> jwtSigningKey=<same-as-local-dev> \
      --parameters n8nUserWebhookUrl=<...> n8nNotificationWebhookUrl=<...> n8nAiWebhookUrl=<...>

    (review the what-if output, then re-run with `create` instead of `what-if`)

Known gotcha hit here: deploying the Container Apps Environment and all 10
apps in ONE deployment made every app's first revision fail with
"Operation expired" - the environment reports Succeeded before it's
actually ready to accept app-create calls. Fix: just re-run the same
`az deployment group create` command again (idempotent) once or twice until
every app shows provisioningState=Succeeded. Took 3 attempts in practice.

Known gotcha #2: the bicep template originally set a `registries` entry on
every Container App at create time (pointing at the ACR, using the app's own
system-assigned identity). This made EVERY app hang and fail identically,
because the identity's AcrPull role assignment (granted in the same
deployment) hadn't propagated yet. Fix, now baked into env.bicep: don't set
`registries` at bootstrap - wire it later via `az containerapp registry set`
once the role assignment has had time to propagate (Step 5).

STEP 4 — Set up GitHub Actions OIDC identity (for automated CD)
-----------------------------------------------------------------------
    az ad app create --display-name "examvault-github-actions-dev"
    az ad sp create --id <appId>
    az ad app federated-credential create --id <objectId> --parameters '{
      "name": "examvault-dev-branch",
      "issuer": "https://token.actions.githubusercontent.com",
      "subject": "repo:<owner>@<ownerId>/<repo>@<repoId>:ref:refs/heads/dev",
      "audiences": ["api://AzureADTokenExchange"]
    }'
    MSYS_NO_PATHCONV=1 az role assignment create --assignee <appId> --role Contributor --scope /subscriptions/<sub>/resourceGroups/rg-examvault-dev
    MSYS_NO_PATHCONV=1 az role assignment create --assignee <appId> --role AcrPush --scope /subscriptions/<sub>/resourceGroups/rg-examvault-shared/providers/Microsoft.ContainerRegistry/registries/acrexamvaultshared

IMPORTANT gotcha: GitHub's OIDC subject claim format is
`repo:<owner>@<ownerId>/<repo>@<repoId>:ref:refs/heads/<branch>` (includes
immutable numeric IDs) - NOT the simpler `repo:<owner>/<repo>:ref:...`
documented in older guides. Get the real subject from the actual
AADSTS700213 error message on a failed run (it tells you exactly what
subject GitHub presented) rather than guessing the format.

IMPORTANT gotcha (Git Bash on Windows): any `az` command with a leading-`/`
`--scope` argument gets mangled by MSYS path conversion
(`/subscriptions/...` becomes `C:/Program Files/Git/subscriptions/...`).
Always prefix with `MSYS_NO_PATHCONV=1` when running from Git Bash.

Status: even after fixing the subject claim, GitHub repo secrets
(AZURE_CLIENT_ID/AZURE_TENANT_ID/AZURE_SUBSCRIPTION_ID) never reached
azure/login@v2 across many attempts - root cause never found (not a naming,
scope, or propagation issue - verified repeatedly). Worked around by
hardcoding the 3 identifiers directly in cd-dev.yml's `env:` block instead
of using secrets (they're not actually sensitive - see Infra/README.md for
the reasoning). GitHub CLI (`gh auth login`) also could not complete its
device-flow login on this machine across 5 attempts (2 different shells,
full user approval confirmed each time) - something in this environment
blocks its polling; abandoned as a diagnostic tool.

STEP 5 — Build, push, and deploy real images (manual route)
-------------------------------------------------------------------
Used because the GitHub Actions CD path (Step 4) hit the unresolved secrets
problem, and `az acr build`'s remote tar-and-upload step separately hung on
this machine (never completed, no ACR task run ever got created - suspected
local resource constraints). Local `docker build` + `docker push` worked
fine as a substitute:

    az acr login --name acrexamvaultshared

    docker build -f <service>/Dockerfile \
      -t acrexamvaultshared.azurecr.io/<service>:dev-<gitsha> \
      -t acrexamvaultshared.azurecr.io/<service>:dev-latest \
      .
    docker push acrexamvaultshared.azurecr.io/<service>:dev-<gitsha>
    docker push acrexamvaultshared.azurecr.io/<service>:dev-latest

    (frontend needs --build-arg VITE_API_BASE_URL=<gateway's external URL>)

Then, per app, wire the registry (now safe - role assignment has propagated)
and roll out the image:

    az containerapp registry set --name <app> --resource-group rg-examvault-dev \
      --server acrexamvaultshared.azurecr.io --identity system
    az containerapp update --name <app> --resource-group rg-examvault-dev \
      --image acrexamvaultshared.azurecr.io/<service>:dev-<gitsha>

Result at this point: all 10 Container Apps running real code. Each
individually confirmed working (e.g. exam-api hit directly returns a
correct 401 on an unauthenticated request in ~22s cold-start).

STEP 6 — Gateway-to-backend networking: unresolved problem, still being
worked (as of last update)
--------------------------------------------------------------------------------------
Symptom: Gateway (YARP reverse proxy) cannot reach ANY backend service
through its normal proxy path - every proxied request either hangs for
~100s and 504s, or fails near-instantly with a low-level TLS handshake
exception (`SslStream.EnsureFullTlsFrameAsync` / `ReceiveHandshakeFrameAsync`
failing to read a complete TLS response frame).

Ruled out one by one (each confirmed NOT the cause via a direct test):
  - Internal vs external ingress on the backend apps
  - HTTP/2 vs HTTP/1.1 (forced via YARP's per-cluster `HttpRequest.Version`/
    `VersionPolicy` config - note this goes under `HttpRequest`, NOT
    `HttpClient`, in YARP's cluster config schema; putting it under
    `HttpClient` is silently ignored)
  - TLS certificate validation (`DangerousAcceptAnyServerCertificate: true`
    made no difference)
  - Forced TLS 1.2 (`SslProtocols: ["Tls12"]` under `HttpClient` - no change)
  - Cold-start timing (`minReplicas: 1` to keep a backend always-warm - no
    change, failure is instant/consistent either way)
  - The specific destination: proxying to `https://management.azure.com`
    (Microsoft's own, always-on endpoint) fails identically - this is NOT
    specific to calling other Container Apps in this environment.
  - The .NET runtime patch version (tested pinning the base image down to
    `mcr.microsoft.com/dotnet/aspnet:8.0.11` instead of the floating `8.0`
    tag - same failure).
  - Missing CA certs (confirmed present and populated inside the container
    via `az containerapp exec`).

Confirmed working: plain HTTP (no TLS) outbound from Gateway's container
works completely fine and fast (e.g. proxying to `http://example.com`
returns a real response in ~1.3s). So this is TLS-specific, not a general
network/egress block.

Also confirmed: Container Apps' `allowInsecure` ingress option (accepts
plain HTTP directly, meant to let a caller skip TLS) does NOT work for
app-to-app calls within this environment either (internal or external) -
both returned Azure's generic "This Container App is stopped or does not
exist" platform error page instead of routing to the real app, suggesting
Container Apps' routing genuinely depends on TLS/SNI to identify the
target, even for allowInsecure apps.

Net conclusion: outbound TLS specifically is broken for this container /
this Container Apps Environment instance, for reasons not identified through
application-level configuration. This affects Gateway AND any other
service's own outbound HTTPS calls (e.g. Submission Service calling Exam
Service), since they use the same base image and same Services__*BaseUrl
pattern - not just a Gateway-specific problem.

UPDATE - environment recreation test completed, same result:
Deleted cae-examvault-dev and all 10 apps, redeployed fresh via
`az deployment group create` against the unchanged Infra/env.bicep (SQL
Server, Service Bus namespace, and the shared ACR were untouched - only the
compute layer was rebuilt). Confirmed genuinely new: new environment default
domain (`purplegrass-5a45369b...` vs the original `bluemoss-9df6d0cb...`).

Gotcha hit during recreation: redeploying the same template against
existing (but now-orphaned) role assignments failed with
`RoleAssignmentUpdateNotPermitted: Tenant ID, application ID, principal ID,
and scope are not allowed to be updated.` - deleting a Container App and
recreating it under the same name gives it a brand NEW system-assigned
identity (new principalId), but the AcrPull role assignment's Bicep-computed
name (`guid(acr.id, app.id, 'AcrPull')`) is deterministic and collides with
the OLD orphaned role assignment (still pointing at the deleted principal).
Fix: list and delete the stale role assignments first
(`az role assignment list --scope <acr-id>` filtered to roleDefinitionName
'AcrPull', then `az role assignment delete --ids <id>` for each), then
redeploy. Needed if this environment is ever recreated again.

RESULT: identical failure in the brand-new environment. Same exact
`SslStream.EnsureFullTlsFrameAsync` / `ReceiveHandshakeFrameAsync` exception,
same instant-fail pattern. This conclusively rules out "this one environment
instance had a fault" - it's not instance-specific. Whatever is breaking
outbound TLS from Container Apps containers in this subscription/region is
either a genuine, currently-active Azure platform issue, or something at the
subscription/tenant level (not the environment level).

Next things worth trying, not yet attempted:
  - Open an Azure support ticket / check Azure status for the centralindia
    region and for Container Apps generally - this is now a strong
    candidate for a genuine platform-level fault, not an app or config bug.
  - Try a completely different Azure region for the dev environment (e.g.
    `centralus` or `eastus`) as a differential test - if a different region
    works, it's region-specific; if it also fails, it's subscription/tenant
    or Container-Apps-product-wide.
  - Try a Container Apps Environment WITH a custom VNet (workload profile)
    instead of the default Consumption-only environment, in case internal
    app-to-app HTTPS specifically needs VNet integration to work reliably
    despite Microsoft's docs saying otherwise.
  - Try Azure App Service or another compute host entirely for just the
    Gateway, as a way to unblock the golden path while the Container-Apps-
    specific issue is investigated separately.

Current workaround in place (temporary, revert once real fix found):
none active as of last update - the last diagnostic step (external +
allowInsecure on exam-api) was reverted back to internal + HTTPS-only.

STEP 7 — What's verified working right now
----------------------------------------------
- All Azure infra (SQL, Service Bus, Container Apps Environment, ACR):
  provisioned, healthy.
- All 10 Container Apps: running real application images (not placeholders).
- Every backend service INDIVIDUALLY (called directly, bypassing Gateway):
  confirmed working correctly (e.g. exam-api's [Authorize] correctly
  rejects an unauthenticated request).
- Frontend: serves its real built page.
- NOT working: Gateway's reverse-proxy path to any backend (Step 6), and by
  extension any feature that depends on it (essentially the whole app, since
  Gateway is the single public entry point) or on server-to-server calls
  between services.
