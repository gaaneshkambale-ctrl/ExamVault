CRITICAL SECURITY FIX, found while scoping ALL USERS (2026-08-23, later
same day) - user supplied `Alluser.png` asking to build the cross-tenant
"All Users" list. Investigating what backend it would need surfaced a
REAL, LIVE cross-tenant data leak that predates this entire multi-tenant
initiative and is unrelated to any mockup: `UserRepository.GetAllAsync`
and `GetByIdAsync` had ZERO tenant scoping - unlike every other entity in
this codebase (which all got proper TenantScopedEntity/EF-filter or
manual-filter treatment in Phase 2), AppUser's own Admin-facing endpoints
were never given the compensating manual scope its "no EF global filter"
design explicitly called for (see AppUser's own comment on why it opts
out of the filter). Concretely, before this fix: ANY tenant Admin's
"Manage Users" page (`GET /api/users`) returned EVERY user across EVERY
tenant, not just their own; and `GET/PUT/DELETE /api/users/{id}`,
`.../reset-password`, `.../sessions`, and `.../photo` let an Admin target
another tenant's user purely by knowing/guessing their Guid - full
cross-tenant view AND mutation (delete, deactivate, password reset).
Fixed: added `GetByIdForTenantAsync` (the same IsSuperAdmin-bypass shape
every other tenant-scoped entity already uses) and switched
Delete/Update/SetActiveStatus/ResetPassword plus the GetById/GetPhoto/
ListSessions controller paths to it; scoped `GetAllAsync` the same way.
Left self-service lookups (own profile/photo, ChangePassword,
RefreshTokenHandler) on the original unscoped `GetByIdAsync` deliberately
- their id is always the caller's own from a validated JWT, or (for
refresh) there's no ambient tenant at all since that endpoint is
anonymous, so scoping there would have broken login itself. `GetById`'s
handler (`GetUserProfileHandler`) needed a `TenantScoped` query flag to
serve both cases correctly rather than forking the handler. Widened
`GET /api/users`'s role gate to `Admin,SuperAdmin` so the new All Users
page could use the now-safe endpoint directly - no new endpoint needed.
Verified live via a real adversarial request (not just code review,
matching this project's own established discipline): a real Tenant B
admin's `GET /api/users` now returns exactly their own 3 users (was:
every user in the system); the Super Admin's own call still correctly
returns all 13 users across all 5 tenants. Backend test suite 335/335,
zero regressions. Also hit and fixed a real frontend type regression
this same fix exposed: widening `UserListItem.role` to admit
`'SuperAdmin'` broke several existing tenant-scoped Admin pages
(ManageUsers.tsx, EditUser.tsx, ResetPassword.tsx, UserDetails.tsx) that
index `Record<UserRole, ...>` or assign to a `UserRole`-typed variable -
`npx tsc --noEmit` alone didn't catch this (different from the project's
actual `tsc -b && vite build` used by `npm run build`/the Docker image),
only the real production build did. Fixed by introducing a separate
`PlatformUserListItem` type (+ `listAllUsers()`) instead of widening the
shared one. Lesson: verify with the actual `npm run build`, not just
`tsc --noEmit`, before rebuilding the Docker image - noted here since
this cost one avoidable rebuild-and-retest cycle.

The "All Users" page itself needed no placeholders at all once the fix
landed - Users Overview/Users by Role (donut, reusing the existing
`SegmentDonutChart`)/Users by Status/Recent Registrations/role
tabs/search are all real, matching `Alluser.png` almost exactly (dropped
only "Suspended"/"Pending" statuses from Users by Status, since no such
user state exists - just IsActive).
