EXAM TYPE (dynamic, DB-backed) + rename existing ExamType -> Creation Method
==============================================================================
Status: PLANNED, not yet implemented.

USER'S ASK (verbatim intent)
-----------------------------
1. The existing "Exam Type" field (Manual / AI Generated) is being renamed to
   "Creation Method" everywhere - label and, since a literal new concept is about
   to take the name "Exam Type", the code symbol too (avoids two different things
   both being called ExamType in the same codebase).
2. "Category" (Technical/Database/Aptitude/Programming/Soft Skills/General) stays
   exactly as it is today - untouched, not part of this feature.
3. A NEW "Exam Type" field is added, holding purpose-based values:
     Practice Exam       - Student practice, usually unlimited/repeated attempts
     Mock Exam           - Simulates the actual examination
     Assessment Exam     - Regular academic/skill assessment
     Competitive Exam    - Competitive/ranked examination
     Certification Exam  - Used to award a certificate
     Entrance Exam       - Admission/selection
     Recruitment Exam    - Hiring/employee assessment
     Internal Exam       - Organization/college internal examination
   This list must be DYNAMIC - stored in the database, admin can add and delete
   entries (not a hardcoded frontend const like EXAM_CATEGORIES is today).

SCOPE DECISIONS (flagged explicitly, not silently assumed)
------------------------------------------------------------
- New entity name: `ExamType` (frees up cleanly once the old enum is renamed to
  `CreationMethod`). Table: ExamTypes. Fields: Id (Guid), Name (string, required,
  max 100), Purpose (string?, max 500 - the "Purpose" column from the table above),
  CreatedAtUtc (DateTime).
- ExamPaper gains a NULLABLE `ExamTypeId` (Guid?) FK. Nullable because existing
  real exams in the database have no value to backfill - forcing it non-null would
  either break existing exams or require guessing a default for each one. New
  exams are NOT required to pick one at creation time (optional field), matching
  how this codebase already treats several settings as optional-with-sensible-default
  rather than mandatory.
- Delete behavior when an ExamType in use is deleted: SET NULL on any exams
  referencing it (DeleteBehavior.SetNull), not blocked. This matches the existing
  precedent in this exact codebase where deleting a Section clears its questions'
  SectionId back to null rather than deleting the questions or blocking the delete.
- CRUD surface: Create + List + Delete only (matches the literal ask "add and
  delete" - no Update/rename endpoint, keeps scope tight).
- api/exam-types: POST (Admin), GET (any authenticated user - the Create/Edit Exam
  dropdown needs to list options for non-admin... actually only Admins create
  exams, but GET stays plain [Authorize] to match the List pattern on every other
  list endpoint in ExamsController/SectionsController), DELETE (Admin).
- ExamResponse gets both `ExamTypeId` (Guid?) AND a denormalized `ExamTypeName`
  (string?) so list/table views don't need a second round-trip per row - matches
  this codebase's established anti-N+1 convention (e.g. Question Service's
  GetOptionsByQuestionIdsAsync batching).
- Sidebar placement: new top-level "Exam Types" nav entry in AdminSidebar.tsx,
  positioned right after "Exams" - NOT nested as a child of "Exams" (would add an
  extra click to the existing single-link "Exams" item) and NOT under Settings
  (this is exam-domain data, matches how "Exams"/"Results"/"Reports" are already
  top-level, not tucked under Settings).
- OUT OF SCOPE for this pass (flagged, not silently dropped): filtering exam
  lists BY the new Exam Type (ManageExams.tsx, MyExams.tsx, AdminReports.tsx
  already filter by Creation Method / Category - adding a third filter dimension
  everywhere is a separate, larger UI pass); CSV import support for Exam Type;
  AI-generated exam auto-assignment of an Exam Type. These can be follow-up asks.
