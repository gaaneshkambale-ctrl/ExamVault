Rule I am following: finish each day fully (Frontend + Backend + Integration +
Verification) before moving to the next day. No skipping ahead.

GIT / CI-CD PUSH RULE
------------------------
- Once each day's work is fully discussed/confirmed as complete, I push the
  code to GitHub.
- Push goes through CI/CD (not a raw push straight to main): commit -> push
  -> CI/CD pipeline runs build + tests -> merge/deploy only if the pipeline
  is green.
- I do not move to the next day until that day's push + CI/CD run has
  succeeded.
- UPDATE: a basic CI workflow (.github/workflows/ci.yml) was set up early,
  right after Day 1, instead of waiting for Phase 10. It builds the backend
  (dotnet restore/build/test) and the frontend (npm ci/build/test) on every
  push and pull request to main. Full CI/CD (container publish, Azure
  deploy, health checks) is still completed in Phase 10 (Day 42) on top of
  this early workflow.

PRINCIPLES I AM KEEPING IN MIND THE WHOLE PROJECT
------------------------------------------------------
- React is the only frontend; it never talks to SQL Server directly.
- YARP Gateway is the single public entry point after Phase 2.
- Each microservice owns its own domain and database.
- Shared projects only hold genuinely cross-service code.
- AI Service never owns the Question DB; AI questions need my approval first.
- Deterministic things (auth, timers, MCQ scoring) never depend on AI.
- RabbitMQ locally, Azure Service Bus in the cloud.
- I never commit secrets to Git.

UI REFERENCE (wireframe.png)
---------------------------------
A wireframe has already been provided (wireframe.png) covering 12 screens:
Landing, Login, Register, Admin Dashboard, Manage Exams, Manage Questions,
Student Dashboard, Take Exam, Exam Result, Profile, Notifications, and
AI Question Generation (Admin).

I am treating this wireframe as the layout reference only (structure, flow,
component placement), and building the final UI to a professional standard
on top of it:
- Consistent design system: one color palette, spacing scale, and typography
  set applied across every screen (not just copied per-page).
- Reusable component library (buttons, cards, tables, form inputs, badges,
  modals) instead of one-off styled elements per screen.
- Responsive layouts for desktop, tablet and mobile, not just the desktop
  frame shown in the wireframe.
- Real interaction states: loading, empty, error and success states for
  every data-driven screen (dashboards, lists, forms).
- Accessibility basics: proper labels, keyboard navigation, sufficient
  color contrast.
- Polish pass at the end of each phase's UI work (Day "Question UI",
  "Exam UI completion", etc.) to bring screens up to production quality,
  not just functional quality.
