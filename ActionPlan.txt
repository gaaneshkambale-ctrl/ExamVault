GIT / CI-CD PUSH RULE
------------------------
- Branch strategy (3-tier): Dev -> QA -> Prod (main).
    Dev  = daily working branch. Every day's commits are pushed here first.
           This is the ONLY branch CI/CD (automated build+test) runs on.
    QA   = staging/testing branch. Receives verified work promoted from Dev
           as a plain merge (no separate CI trigger on QA).
    Prod = main branch, production/stable. Receives verified work promoted
           from QA at phase gates / release points (no separate CI trigger
           on Prod either, until Phase 10 sets up real deployment CD).
- Daily flow: commit -> push to Dev -> CI runs build + tests on Dev ->
  once that day's work is confirmed/verified -> merge Dev -> QA.
- Promotion flow: QA -> Prod (main) happens at phase gates / release
  points once QA has been confirmed stable.
- I do not move to the next day until that day's push to Dev + CI run has
  succeeded. QA and Prod promotions happen once a day's or phase's work is
  verified, not on every single commit.
- UPDATE: a basic CI workflow (.github/workflows/ci.yml) was set up early,
  right after Day 1, instead of waiting for Phase 10. It builds the backend
  (dotnet restore/build/test) and the frontend (npm ci/build/test) on every
  push and pull request to Dev ONLY. Full CI/CD (build+test on all
  branches, container publish, Azure deploy, health checks) is still
  completed in Phase 10 (Day 43) on top of this early workflow.

Backend:

- I am adding unit tests for the refresh and logout handlers (valid,

DECISIONS LOCKED IN FOR PHASE 8
------------------------------------
- Result Service owns no database at all, the same design already used
  for AI Service (Day 27) - it computes a result on demand by
  orchestrating read-only calls to the services that already own the
  real data (Submission Service for the attempt/answers, Question
  Service for the answer key, Exam Service for pass-mark/total-mark
  metadata), rather than storing a second, syncable copy of a score
  anywhere. If a question or an attempt's answers ever changed, a
  stored score could silently go stale - computing it fresh every time
  avoids that class of bug entirely.
- Question Service's existing GET /api/questions endpoint masks
  IsCorrect to false for non-Admin callers (the Day 32 fix, so a
  student can't read answers through Take Exam). Result Service needs
  the real answer key to grade anything, so I am adding a second,
  internal-only endpoint to Question.API that returns unmasked
  correct-answer data. The Gateway's existing questions-route already
  proxies everything under /api/questions/{**catch-all} to Question
  API, so nesting the new endpoint under /api/questions would still
  let a browser reach it through the Gateway despite my intent -
  instead it lives outside /api entirely (GET
  /internal/questions/answer-key), a path the Gateway has no route
  for at all, so a request to it through the Gateway (:5000) 404s
  before ever reaching Question API. Only another backend service
  calling Question API directly on its own port (:5030) can reach it.
  This preserves the Day 32 invariant (students never see correct
  answers before/without submitting) while still giving Result
  Service what it needs to grade.
- Result Service reuses Submission Service's existing GET
  /api/submissions/mine?examId= (Day 33) for the attempt/answers,
  rather than adding a new by-attemptId endpoint - "mine" already
  returns exactly the caller's own most recent Submitted/AutoSubmitted
  attempt with the "can't see another user's attempt" guarantee built
  in by construction. This means Result Details shows the most recent
  attempt only; if MaxAttempts allows more than one attempt on an
  exam, older attempts are not individually viewable. This is the same
  kind of accepted, explicitly-flagged simplification as Day 33's
  "no visible retake action" gap, not a silent limitation.
- Whether a student sees a score at all, and whether they see which
  answers were right/wrong, is controlled by the assignment's
  ShowResultsAfterSubmit and ShowCorrectAnswers settings (added by the
  exam-assignment feature after Phase 7, the more specific/authoritative
  per-assignment settings) rather than the older Phase 5 exam-level
  ShowResult/ShowCorrectAnswers fields, which were never wired to
  anything real and stay that way - a known duplication, not resolved
  in this phase since it was not asked for.

WIREFRAME SCOPE NOTE FOR PHASE 9
-------------------------------------
A dedicated Notification.png wireframe (6 screens: Notification Details,
Create Notification, Notification History, Notification Settings, Admin
Notification Details, Mobile Inbox) arrived mid-phase, after Day 37 had
already started under a lighter, no-mockup design. This note replaces
the original one, which assumed no dedicated mockup existed.

Real scope beyond the original design: notifications are no longer only
event-triggered. An Admin can author and send a broadcast notification
by hand (Create Notification screen) to All Students, Selected Students,
Specific Exam Candidates, or Admins, either immediately or "for later."
Every notification - system-triggered or admin-authored - shows up
together in one Admin-facing History table with per-notification
recipient/delivery counts, a details drill-down, and resend/delete
actions. Students (and Admins, for their own inbox) get a per-type
In-App/Email preference grid (Notification Settings) and a delete
action on their own notification detail view, on top of the
mark-as-read flow already scoped for Day 38.

Three explicit scope decisions, made with the user mid-phase since none
of them were derivable from existing code:
- Email is real, sent through an n8n workflow over a Gmail account (an
  n8n Webhook node -> Send Email node), not a direct SMTP integration
  in .NET. The Notification Service only ever does one thing: HTTP
  POST a small JSON payload to a configured n8n webhook URL. This keeps
  no SMTP credentials in this codebase at all, and matches n8n's own
  strength (workflow/credential management) instead of duplicating it
  in code.
- SMS is dropped entirely, not just left unimplemented - no SMS column
  exists anywhere in the Settings UI or the Notification schema. The
  wireframe's SMS toggle would otherwise be dead UI with nothing behind
  it, which this project's own conventions call out to avoid.
- "Schedule For Later" is store-only: the admin's chosen send time is
  saved (`ScheduledAtUtc`) and the batch is created immediately, but no
  background dispatcher exists to act on it. A scheduled batch becomes
  visible to recipients automatically once its time passes - a side
  effect of every "mine" read filtering on
  `ScheduledAtUtc IS NULL OR ScheduledAtUtc <= UtcNow`, not a real job -
  and it never triggers an email attempt. Flagged here as an explicit,
  deliberate gap, the same honesty this plan has used for every other
  not-yet-buildable trigger.

Also dropped as inapplicable rather than deferred: the wireframe's
"Certificate Available" notification type. No certificate feature
exists anywhere in this codebase (My Certificates was already flagged
as a Phase 7 gap) - a toggle for a feature that doesn't exist would be
pure decoration, so the Settings grid only covers the five types this
codebase can actually trigger or author: Exam, Reminder, Result,
System, Account.

Given the real scope increase, Phase 9 grows from 2 days to 3 (Days
37-39), the same 3-day shape Phase 8 used for a similarly-sized
service.

DECISIONS LOCKED IN FOR PHASE 9
------------------------------------
- Notification Service gets a real database (`ExamVault.NotificationDb`)
  - the one deliberate exception to the DB-less design AI Service (Day
  27) and Result Service (Day 34) both established. A notification is
  inherently something a user reads later, not a value recomputed
  fresh on every request.
- Every notification - system-triggered or admin-authored - is one row
  per recipient in a single `Notification` table, tagged with a shared
  `BatchId` per trigger. Admin History/Details aggregate with a
  `GROUP BY BatchId` query rather than a separate campaign/header
  table - the smallest structure that answers the question, not a
  premature entity.
- Exam Service's `CreateAssignmentHandler` becomes the second-ever
  event publisher in the codebase (after `RegisterUserHandler`) - its
  own `RabbitMqEventPublisher` copy in `Exam.Infrastructure`, matching
  this codebase's established preference for a small per-service copy
  over a shared abstraction.
- `ExamAssignedEvent` carries resolved `Email`/`FullName` per target
  user (a new `AssignedUserInfo` list, not bare `Guid` ids) - the
  Worker that consumes it has no HTTP caller and therefore no bearer
  token to look anything up with, and this codebase has never
  introduced a service-account/client-credentials flow. Resolving
  email/name at publish time (`CreateAssignmentHandler` already holds
  the admin's own token) avoids inventing one now.
  `UserRegisteredEvent` already carries Email/FullName and needs no
  change.
- `IUserLookupClient` (Exam Service) gains `GetUsersByIdsAsync` -
  implemented the same way `GetAllStudentUserIdsAsync` already is:
  call the existing `GET /api/users` (there is no id- or role-filtered
  endpoint on User Service) and filter client-side, rather than adding
  a new User Service endpoint for a one-off need.
- The Worker keeps its established one-`BackgroundService`-per-event-
  type shape - `UserRegisteredConsumer` goes from log-only to
  persisting + emailing; `ExamAssignedConsumer` is new, not merged
  into the first.
- A shared `NotificationPersistenceService` in
  `Notification.Infrastructure` (create rows + resolve per-recipient
  email preference + call the email dispatcher) is used by both the
  Worker (event-triggered path) and `Notification.API` (admin-
  authored, Send Now path) - the one piece of logic both paths need,
  factored once rather than duplicated.
- Email delivery is real but goes through n8n, not a .NET SMTP client
  - `Notification.Infrastructure` gets a small
  `IEmailDispatcher`/`N8nEmailDispatcher` that POSTs
  `{ toEmail, toName, subject, body, type, notificationId }` to a
  configured webhook URL and records the per-recipient outcome
  (`Delivered`/`Failed`) on the `Notification` row. A recipient with
  the type's Email preference off gets no attempt at all and is still
  counted `Delivered` for in-app purposes.
- Admin broadcast targeting (`Create Notification`) does need cross-
  service HTTP calls after all - `GET /api/users` (User Service) for
  All Students/Selected Students/Admins, and the existing
  `GET /api/assignments?examId=` (Exam Service, already returns
  resolved `TargetUserIds` per assignment) for Specific Exam
  Candidates - forwarding the admin's own JWT exactly like every other
  cross-service call in this codebase. This reverses the original Day
  37 assumption that Notification Service would need zero cross-
  service calls; that assumption only ever held for "mine" reads, not
  admin-authored writes.
- Notification Settings only covers the five types this codebase can
  actually trigger: Exam, Reminder, Result, System, Account - no
  `Certificate Available` row (no certificate feature exists), no SMS
  column (dropped per the user's decision).

POST-PHASE-9 FIX (2026-08-15): n8n notification email AI Agent was
hallucinating unrelated content
-----------------------------------------------------------------------
FIXED. The n8n notification-email workflow's "Build Email Content" Set
node wasn't forwarding body.body/body.type downstream to the AI Agent,
so the Agent received an effectively empty message and fabricated
unrelated replies (e.g. a Result-type message for a Reminder
notification, or a conversational "please provide the message" reply).
Fixed by forwarding those fields (includeOtherFields + explicit
assignments) and hardening the AI Agent's prompt with an
anti-hallucination guard (fixed EMPTY_SOURCE_MESSAGE sentinel on empty
input instead of inventing content) and a mandatory-rewrite rule
(returning the input verbatim is never acceptable - grammar/phrasing
must always be corrected). Verified live against the real n8n webhook
across all 5 notification types (Exam/Reminder/Result/System/Account)
and a long multi-detail message, confirming exact facts (dates, times,
marks, topic lists) are preserved while wording is properly
rewritten. Checked-in copies (Documentation/n8n-notification-
workflow.json, Backend/Services/NotificationService/workflow.txt)
updated to match the confirmed-working live workflow. Full
investigation, every intermediate test result, and the complete
before/after prompt are in FeatureUpdate.txt at the repo root.

POST-PHASE-9 FIX (DONE, 2026-08-17): "Confirm & Assign" on
/admin/assignments/new fails with "Something went wrong" even though
the assignment was actually created
-----------------------------------------------------------------------
ISSUE RAISED: clicking "Confirm & Assign" on step 4 of the Assign Exam
wizard shows a red "Something went wrong. Please try again." banner.

ROOT CAUSE (reproduced live against the Docker stack, confirmed via
exam-api container logs and a direct DB query): CreateAssignmentHandler
successfully validates the request, writes the ExamAssignment +
ExamAssignmentTargets rows, THEN calls
_eventPublisher.PublishAsync(new ExamAssignedEvent {...}) unguarded.
RabbitMqEventPublisher (Exam.Infrastructure/Messaging) is registered as
a Singleton whose constructor calls
factory.CreateConnectionAsync() exactly ONCE and caches the resulting
Task<IConnection> for the process's entire lifetime - if that one
connection attempt fails for any reason (RabbitMQ not fully accepting
AMQP connections yet at exam-api startup, which is exactly what
happened in this Docker session per the container logs -
BrokerUnreachableException: Connection refused), every later publish
throws the same cached exception forever, with no retry, until exam-api
itself restarts. That exception is unhandled, so the whole HTTP request
fails with a raw 500 that doesn't match any shape extractServerError
recognizes (no `message`/`detail`/`errors` field) - hence the generic
fallback text.

CONFIRMED VIA REPRO: clicked Confirm & Assign twice against the c# exam
- both times the UI showed the error, but a direct SQL query against
ExamDb.ExamAssignments showed BOTH attempts had actually inserted a row
(AssignmentNumber 1004 and 1005) before the crash. So today's bug is
worse than a cosmetic error message: the write silently succeeds, the
Admin is told it failed and is invited to retry, and retrying creates a
duplicate assignment. It also means the ExamAssignedEvent never
reaches Notification Service, so assigned students never get notified.

DECISION: match the "best-effort side channel" principle already
established in this codebase for CreateUserHandler's invite email (a
downstream notification failing must not fail the operation that
already durably succeeded) - wrap the ExamAssignedEvent publish in
try/catch, log a warning on failure, and still return success from
CreateAssignmentHandler since the assignment itself is valid and saved.

OUT OF SCOPE, FLAGGED BUT NOT FIXED NOW: the deeper fragility - a
Singleton RabbitMqEventPublisher that permanently breaks after a single
failed connection attempt, no reconnect/retry - is duplicated
per-service (also present verbatim in
UserService's RegisterUserHandler, same unguarded PublishAsync call).
Only the ExamService/CreateAssignmentHandler symptom is being fixed
here, since that's what was reported; the same class of bug could
resurface anywhere else in the codebase that publishes an event after a
RabbitMQ startup hiccup. Worth a dedicated resiliency pass later if the
user wants it.

IMPLEMENTATION: CreateAssignmentHandler.cs - add
ILogger<CreateAssignmentHandler> (same DI pattern as
CreateUserHandler), wrap the PublishAsync call in try/catch logging a
warning, keep returning CreateAssignmentResult.Ok(...) either way.
Exam.Application.csproj needed an explicit
Microsoft.Extensions.Logging.Abstractions package reference added
(User.Application gets ILogger transitively via
Microsoft.Extensions.Identity.Core; Exam.Application has no such
dependency) - same package/version already used by Ai.Application and
Result.Application.

TESTS: FakeEventPublisher (Exam.Application.Tests/Fakes) got a
ShouldThrow flag to simulate a broker failure. New test
Event_publish_failure_does_not_fail_an_otherwise_valid_assignment
confirms the assignment still saves and HandleAsync still returns
Success when the publish throws. Full Exam.Application.Tests run:
52/52 passed (was 51). Full solution build (Release): 0 errors.

LIVE-VERIFIED in Docker: rebuilt exam-api with the fix, reran the exact
repro (Assign Exam wizard -> Confirm & Assign against the real "c#"
exam, All Students target) - got "Exam Assigned Successfully!"
(ASG-1006), and exam-api's logs show no warning at all (RabbitMQ was
fully warm by then, so the publish just succeeded normally this time -
the try/catch is a safety net for the next time the broker hiccups at
startup, not something that fires on every request).

CLEANUP MISTAKE: while clearing out the two duplicate test assignments

DECISIONS LOCKED IN (proposed defaults - flagged for override, not
silently assumed)
--------------------------------------------------------------------
1. SQL Authentication everywhere, no exceptions. Not really a choice -
   Windows Integrated Auth has no meaning inside a Linux container or
   against Azure SQL. Every connection string becomes
   `Server=...;Database=...;User Id=...;Password=...;
   TrustServerCertificate=True;`, values supplied by environment
   variables (local Docker Compose `.env`) or Container Apps secrets
   (Azure), never hardcoded. [MANDATORY]
2. Messaging stays dual-provider: RabbitMQ for local Docker Compose
   (unchanged), Azure Service Bus for the Azure deployment, selected
   by a `Messaging:Provider` config switch - honors the pre-existing
   "RabbitMQ locally, Service Bus in the cloud" principle instead of
   migrating everything to Service Bus and losing today's zero-cost
   local dev loop, or keeping RabbitMQ in Azure and quietly dropping a
   decision already made. [DEFAULT, override if you'd rather run
   RabbitMQ in Azure too via a container - simpler, one less thing to
   learn, but breaks the stated principle.]
3. Azure hosting model: Azure Container Apps for every backend service
   AND the frontend (consumption-based, scale-to-zero when idle - the
   cheapest realistic fit for a low-traffic portfolio project, and one
   consistent hosting model instead of mixing Container Apps + App
   Service + Static Web Apps). [DEFAULT, override if you'd rather use
   Azure Static Web Apps for the frontend specifically (also free-
   tier-friendly, purpose-built for a static Vite/React build, and
   needs no Dockerfile at all for the frontend) or App Service instead
   of Container Apps (more familiar UI, no scale-to-zero, generally
   pricier for 9 always-on-ish processes).]
4. Database hosting: one Azure SQL logical server, serverless/Basic
   tier, hosting all 6 databases - mirrors today's "one local SQL
   Server instance, many databases" shape exactly, and is the cheapest
   PaaS option. [DEFAULT, override if you'd rather containerize SQL
   Server itself (cheaper still, no Azure SQL vCore/DTU cost, but you
   lose PaaS automatic backups/HA and own patching yourself).]
5. Secrets in Azure: Container Apps' built-in secrets (referenced as
   env vars per app), not Azure Key Vault - Key Vault is the more
   "enterprise" answer but is extra cost and setup for a project this
   size with no compliance requirement driving it. [DEFAULT, override
   if you want Key Vault specifically, e.g. for portfolio/interview
   value of showing it.]
6. CI/CD deploys on push to `main` (not `dev`) - matches this repo's
   existing branch convention where `dev` is the working branch and
   `main` is the stable/release branch. [DEFAULT, override if you want
   `dev` pushes to auto-deploy to a staging environment too - bigger
   scope, a second environment to provision and pay for.]
