    trigger anywhere in the codebase. Grepping every backend project for
    where a NotificationType is actually set shows only two real

    composes and sends one via Create Notification - they are not
    system-generated. This wasn't a bug found today, but it IS a real gap
    worth being explicit about: the notification-email fix tested all 5

    Settings)" but DashboardSidebar.tsx has no submenu/children structure

    a single "Notifications" -> /notifications entry. A student can only
    reach /notifications/settings by typing the URL directly or via a

    notification emails (HTML email + <img> tag). Last live test attempt
    broke the n8n workflow (HTTP 500) due to a copy-paste escaping mistake
    in the n8n UI, root cause identified (JSON-escaped text pasted

4. NEW FEATURE PLAN (2026-08-15): Automatic Exam Reminder
--------------------------------------------------------------------
STATUS: PLANNED - NOT IMPLEMENTED YET (design only, per plan-before-code rule)

FEATURE: close gap 2(a) above - automatically send a Reminder-type
notification (in-app + email, reusing the existing pipeline) to every
student assigned to an exam, ahead of the assignment's start time,
without any Admin having to compose it by hand.

DECISIONS CONFIRMED WITH THE USER (none derivable from existing code):
1. Timing: TWO reminders per assignment per student - one ~24 hours
   before the assignment's StartAtUtc, one ~1 hour before.
2. Recipients: everyone assigned to the assignment, regardless of
   attempt/submission status - matches how ExamAssignedEvent already
   notifies "everyone assigned" with no Submission Service check. No new
   cross-service call to Submission Service is introduced by this
   feature.
3. Job location: a new periodic background job lives inside Exam
   Service (Exam.API), not Notification Service/Worker - Exam Service
   already owns all assignment/timing data in its own DB, so no new
   cross-service HTTP call or auth flow is needed to find "assignments
   starting soon." This mirrors the existing precedent of a per-service
   background component (the Worker's consumers) rather than introducing
   a new internal-endpoint-plus-anonymous-polling pattern.

DESIGN (mirrors the existing ExamAssignedEvent / ExamAssignedConsumer
shape as closely as possible - no new architectural pattern introduced):

Exam Service side (new):
- New `ExamReminderCheckService` : BackgroundService in Exam.API (or
  Exam.Infrastructure, DI-registered from Exam.API - matches where the
  Worker's consumers live relative to Notification.Infrastructure).
  Runs on a `PeriodicTimer`, proposed interval 5 minutes (tunable later,
  not a decision that changes the design - flagged here rather than
  asked as a separate question).
- Each tick, for each of the two windows (24h, 1h) independently: query
  ExamAssignments belonging to Published exams where
  `0 < (StartAtUtc - UtcNow) <= window` (range check, not an exact
  timestamp match - robust against imprecise tick timing or occasional
  missed ticks, unlike trying to catch an exact instant).
- New small table `ExamReminderLog` (AssignmentId, UserId,
  ReminderWindow enum [TwentyFourHour, OneHour], SentAtUtc) with a
  unique constraint on (AssignmentId, UserId, ReminderWindow) - the
  idempotency guard so the same reminder is never published twice for
  the same assignment/student/window, no matter how many ticks land
  inside that window before it closes.
- For each (assignment, window) pair with at least one un-logged target:
  resolve target users via the EXISTING `IUserLookupClient.
  GetUsersByIdsAsync` (added for ExamAssignedEvent, reused as-is - no
  new client needed), insert `ExamReminderLog` rows for every target
  about to be notified (write-then-publish, so a crash after the DB
  write but before publish just skips that tick's send rather than
  double-sending - acceptable at-most-once tradeoff, consistent with
  this codebase's existing "email is best-effort" tolerance elsewhere),
  then publish one new `ExamReminderDueEvent` (`Shared.Events`) carrying
  ExamId, AssignmentId, ExamTitle, StartAtUtc, ReminderWindow, and
  `Targets: IReadOnlyList<AssignedUserInfo>` - same shape as
  ExamAssignedEvent, via Exam Service's existing RabbitMqEventPublisher
  (no new publisher plumbing needed, it already exists from Day 37).

Notification Worker side (new):
- New `ExamReminderConsumer` : BackgroundService (own queue, e.g.
  `notification-service.exam-reminder-events`) - same
  one-BackgroundService-per-event-type shape as
  UserRegisteredConsumer/ExamAssignedConsumer. Builds the message text
  based on ReminderWindow ("Your exam '{title}' starts in 24 hours" /
  "starts in 1 hour"), persists + emails via the existing
  NotificationPersistenceService (Type=Reminder, RelatedExamId set) -
  no changes needed to NotificationPersistenceService itself.

KNOWN LIMITATIONS (flagged, not engineered around - consistent with how
"Schedule For Later" store-only was flagged rather than fully solved):
- If the Exam Service process is down across an entire reminder window
  (e.g. down for 2+ hours spanning when the 1h reminder should have
  fired), that reminder is simply missed - no catch-up/backfill logic.
  Given reminders are a convenience feature, not a correctness-critical
  one, this tradeoff is accepted rather than building a more complex
  catch-up scheduler.
- No per-user reminder preference beyond the existing Notification
  Settings page's Reminder row (In-App/Email toggle) - a student who
  turns Reminder emails off simply gets no email attempt for these,
  exactly like any other type, no new preference needed.

6. FEATURE (2026-08-15): make the 24h/1h reminder windows togglable
   via a global Admin setting
--------------------------------------------------------------------
STATUS: DONE - IMPLEMENTED AND VERIFIED LIVE

REQUEST: today the two reminder windows (24h, 1h) are hardcoded constants
in ExamReminderCheckService.Windows - there is no way to disable one of
them, or to see/change this from the app at all. User wants a real
setting for this.

DECISIONS CONFIRMED WITH THE USER:
1. Scope: ONE GLOBAL setting, not per-exam - applies to every exam
   assignment app-wide. (Per-exam configurability was considered and
   explicitly not chosen.)
2. Shape: toggle the two EXISTING windows on/off (two checkboxes: "Send
   24-hour reminder" / "Send 1-hour reminder"), not fully custom hour
   values. This keeps ReminderWindow as a fixed 2-value enum and the
   whole range-check/dedupe/publish code path unchanged - only whether a
   given tick even attempts a window changes.

DESIGN:
- New global settings row in Exam Service's own DB (it already owns the
  reminder job) - a single-row table `ReminderSettings` (Id fixed to a
  well-known GUID or just "the only row", Enable24HourReminder bool,
  Enable1HourReminder bool). Both default to true, so a fresh deploy or
  a database with no row yet behaves exactly like today (both windows
  on) - no migration-time behavior change for existing installs.
- New Admin-only endpoints on Exam.API: GET/PUT
  `/api/exams/reminder-settings` (Gateway already proxies everything
  under /api/exams/{**catch-all}, so no new Gateway route needed) -
  [Authorize(Roles="Admin")], mirroring the existing thin
  Command/Query+Handler shape used everywhere else in this codebase.
- `ExamReminderCheckService` reads the current settings once per tick
  (cheap single-row query, no caching needed at a 5-minute cadence) and
  skips a window entirely if its toggle is off - e.g. if
  Enable1HourReminder is false, the 1-hour window is never checked or
  published for any assignment, app-wide, until turned back on.
- Frontend: a new "Exam Reminders" section on the existing Admin
  Settings page (/admin/settings, AdminSettings.tsx - currently just
  Change Password + a link to Notification Settings) - two checkboxes
  and a Save button calling the new PUT endpoint. Matches the plan's own
  "Admin Settings page already exists, extend it" precedent rather than
  creating a new settings page.

NOT DECIDED YET / open follow-up, not blocking this plan: whether
turning a window off should also delete or keep already-logged
ExamReminderLog rows for that window - proposed default is to just leave
them (a toggle only affects whether FUTURE ticks check that window; past
history is left alone, same "never silently rewrite history" instinct as
everywhere else in this app). Flagging rather than deciding unilaterally
in case the user wants different behavior when they see it.

NEXT STEP: implement top-down once this plan is confirmed - entity +
migration -> repository/handler -> controller endpoints -> background
job reads the setting -> frontend Admin Settings section -> verify live
(toggle 1-hour off, confirm a real assignment's 1-hour window is skipped
while 24-hour still fires; toggle back on, confirm it resumes).

7. NEW FEATURE PLAN (2026-08-15): Admin invites a user by email only -
   auto-generated password, emailed, forced reset on first login
--------------------------------------------------------------------
STATUS: PLANNED - NOT IMPLEMENTED YET

REQUEST: Admin creates a user (today: Full Name/Email/Password/Confirm/
Role/Phone/Active, Admin types the password). New flow: Admin no longer
types a password - the system generates one, emails it to the user, the
user logs in with that temporary password, and is forced to set a real
password of their own choosing before they can reach their dashboard.

--------------------------------------------------------------------
7a. RESEARCH FINDINGS (2026-08-15, via a fork - facts, not assumptions)
--------------------------------------------------------------------
- AppUser (Domain/Entities/AppUser.cs) has no password-state flag at all
  today - no MustChangePassword, nothing like it.
- LoginUserResult only carries Success/IsAccountDeactivated/User/
  AccessToken/RefreshToken - no signal a frontend could use to force a
  reset flow.
- The only existing "reset password" endpoint (PUT /api/users/{id}/
  reset-password) is [Authorize(Roles="Admin")] ONLY - an Admin resetting
  ANY user's password to a value THEY type, no old-password check, no
  email sent. It is not self-service. A Student today has NO endpoint at
  all to change their own password - a real, pre-existing gap this
  feature will need to close as a side effect.
- CreateUserCommand requires Password today (validated: 8+ chars, upper,
  lower, digit) - Admin types and confirms it in CreateUser.tsx today.
- Post-login redirect happens inline in LoginForm.tsx right after
  login() resolves - purely role-based (Admin -> /admin/dashboard,
  Student -> /dashboard). No intermediate gate exists today.
- The login modal's "Forgot Password?" is a plain <span> with no onClick
  and no href - confirmed completely dead, not wired to anything. No
  forgot-password backend endpoint/token/email flow exists anywhere in
  the codebase. Out of scope here (see 7d) but flagged as a natural
  future use of the same "email a credential" plumbing this feature adds.
- Every existing email goes out through NotificationPersistenceService +
  N8nEmailDispatcher, and NotificationPersistenceService ALWAYS persists
  the message body as a real, queryable Notification row (visible to the
  recipient on their own /notifications page indefinitely, and to any
  Admin drilling into Notification History). Reusing this pipeline
  unmodified for a temporary password would leave that password sitting
  in plaintext in the database forever, readable by the user any time
  and by any Admin - a real security gap, not a stylistic one. This
  feature must NOT go through NotificationPersistenceService.

--------------------------------------------------------------------
7b. DECISIONS (proposed defaults - flagged for the user to override,
    not silently assumed)
--------------------------------------------------------------------
1. Applies uniformly to any role Admin creates (Student or Admin) - no
   role-specific special-casing, since the mechanism doesn't need to
   differ by role. [DEFAULT, override if you want this Student-only.]
2. CreateUser.tsx drops the Password/Confirm Password fields entirely -
   under this feature, Admin can no longer choose a user's initial
   password by hand. [DEFAULT, override if you'd rather keep manual
   password entry as an option alongside auto-generate.]
3. The forced first-login password change requires re-entering the
   current (temporary, emailed) password, not just picking a new one -
   standard practice, prevents a leaked/observed access token being used
   to silently change the password without knowing the current one.
   [DEFAULT, override if you want it skippable.]
4. Once built, the new self-service "change my own password" capability
   is also reachable any time afterward from the user's own Profile page
   - not just once during the forced flow - since Students otherwise
   have literally no way to ever change their own password. [DEFAULT,
   override if you want it forced-flow-only.]
5. NOT a preference, a security decision: the temporary password is
   delivered via a NEW, separate email path that never persists the
   plaintext password anywhere in this app's own database - see 7c for
   exactly how.

7c. DESIGN

BACKEND - User Service:
- AppUser gains `MustChangePassword` (bool, default false) - new
  migration on UserDb.
- New `IPasswordGenerator` (Application interface) + implementation
  (Infrastructure) - generates a random password that satisfies
  CreateUserValidator's existing rules (8+ chars, upper, lower, digit),
  built from `RandomNumberGenerator` (cryptographically secure), not
  `Random`.
- CreateUserCommand drops Password/ConfirmPassword - CreateUserHandler
  generates the password via IPasswordGenerator, hashes+stores it, sets
  MustChangePassword = true.
- Email delivery: User Service gets its OWN small IEmailDispatcher/
  N8nEmailDispatcher copy (its own HttpClient pointed at the same
  N8n:WebhookUrl config) rather than routing the plaintext password
  through Shared.Events/RabbitMQ to the Notification Worker. Rejected
  alternative, and why: publishing a `UserInvitedEvent` carrying the
  temp password would put that plaintext password onto the shared
  RabbitMQ exchange (a durable, on-disk message until consumed) - a
  larger blast radius than a direct, synchronous HTTP call from User
  Service straight to the n8n webhook. This also matches the codebase's
  own established "small per-service copy over shared abstraction"
  precedent (already used for RabbitMqEventPublisher) and its existing
  treatment of the n8n webhook URL itself as a credential (Day 37 note:
  "possessing the URL alone is enough to invoke the workflow"). The
  email is sent directly inside CreateUserHandler's flow (Type=Account
  tone, matching the n8n AI-rewrite prompt's existing Account category) -
  no Notification row is ever created for it.
- LoginUserResult (and the UserProfileResponse the controller builds)
  gain `MustChangePassword`, so the frontend gets the signal immediately
  after a successful login.
- New self-service endpoint: `PUT /api/users/me/password`
  ([Authorize], any authenticated role, operates on the caller's own id
  from the JWT - same CallerId-from-claims pattern already used in
  NotificationsController) - ChangePasswordCommand(UserId,
  CurrentPassword, NewPassword), handler verifies CurrentPassword via
  IPasswordHasher.VerifyHashedPassword (rejects with a specific error if
  wrong), then hashes+stores NewPassword and sets MustChangePassword =
  false. The existing Admin-only PUT /api/users/{id}/reset-password stays
  exactly as it is today (still useful e.g. if an invite email bounces).

- CreateUser.tsx: remove Password/Confirm Password fields + the
  "password must contain" checklist; add a short note ("A temporary
  password will be emailed to this address.").
- Login response now carries mustChangePassword; LoginForm.tsx's

- New /change-password page (Current Password / New Password / Confirm)

6. Partial-failure handling on actual submission (e.g. a duplicate email
   that only the backend can catch) matches Day 29's exact pattern:
   successfully created rows are removed from the pending list,
   failed rows stay visible with their server-returned error reason
   (e.g. "already exists") and are not silently retried or merged into
   an existing account. [DEFAULT - no "update existing user" behavior on
   duplicate email, since that's a different, riskier operation not

8e. IMPLEMENTATION NOTES (deviations from the 8a/8b plan text)
--------------------------------------------------------------------
1. DEPENDENCY SWAP: `xlsx` (SheetJS), named as the example library in
   8a.2, was NOT used. `npm install xlsx` succeeded but `npm audit`
   flagged it high-severity - Prototype Pollution (GHSA-4r6h-8v6p-xvw6)
   and a ReDoS (GHSA-5pgg-2g8v-p4x9), both "No fix available". Per the
   standing security rule (don't ship known-vulnerable code), swapped to
   `read-excel-file` + `write-excel-file` (same author/ecosystem as
   SheetJS alternatives, actively maintained, browser-first). `npm audit`
   confirmed 0 vulnerabilities after the swap. Duplicate-email-in-file
   checking (not in the original 8a list) was added to validateRow() as
   a natural extension of "required Full Name/Email; Role must match
   exactly" - a file with the same email on two rows now flags both rows
   rather than silently letting the second overwrite/duplicate.
2. PACKAGE EXPORT GOTCHA: both packages only expose subpath exports
   (`read-excel-file/browser`, `write-excel-file/browser`, plus `/node`,
   `/universal`) - there is no bare `"."` export. Importing the bare
   package name (`import readXlsxFile from 'read-excel-file'`) resolves
   at the type level but fails at Vite dev-server runtime with "'.' is
   not exported under the conditions [...] from package ...", which
   silently blanked the whole page (React never mounted, #root stayed
   empty, no console error - only visible via the page's
   <vite-error-overlay> shadow DOM). Fixed by importing from the
   `/browser` subpath explicitly in ImportUsers.tsx.
3. API SHAPE GOTCHA: the default export of `read-excel-file` (this
   installed version) returns `Promise<Sheet[]>` where
   `Sheet = { sheet: string; data: Row[] }` - NOT `Promise<Row[]>`
   directly, despite that being the historically documented shape for
   this library. Code originally did `sheet.slice(1)` on the resolved
   value (a single-element array), which produced an empty slice and
   showed "The file has no data rows below the header" even for a
   correctly-formed file. Fixed to `sheets[0].data.slice(1)`. Both
   gotchas were caught during live verification (see 8f), not before.

the temp password emailed to them, and got "Your account has been
deactivated. Contact an administrator." instead of being logged in.

email+password verification succeeds, so this message can only appear
for a genuinely correct login - it was never a credentials problem.
Root cause is 8g/8h: since new accounts default to Inactive, and login
rejected on IsActive == false, no new user could ever complete their
first login, meaning the temp-password email now led to a dead end
requiring the Admin to manually Activate the account first every single
time - undermining the entire point of self-service first login.

password, MustChangePassword == true) should be let through to the
existing forced Change Password screen despite IsActive == false, and
completing that password change should auto-activate the account.
Admin-deactivated accounts (IsActive turned off on a user who already
finished onboarding, so MustChangePassword == false) must remain fully
blocked at login, unchanged.

IMPLEMENTATION:
- LoginUserHandler.cs: the rejection condition changed from
  `if (!user.IsActive)` to `if (!user.IsActive && !user.MustChangePassword)`.

  /change-password (LoginForm.tsx already redirects there whenever
  profile.mustChangePassword is true - no frontend change needed). A

  exactly as before, since MustChangePassword is false for it.
- ChangePasswordHandler.cs: on a successful password change, now also
  sets user.IsActive = true alongside the existing
  user.MustChangePassword = false. This is a no-op for a voluntary
