2. FEATURES STILL PENDING / GAPS (found by reading the actual code)
--------------------------------------------------------------------

(a) Reminder, Result, and System notification types have NO automatic
    trigger anywhere in the codebase. Grepping every backend project for
    where a NotificationType is actually set shows only two real
    triggers: NotificationType.Exam (ExamAssignedConsumer) and
    NotificationType.Account (UserRegisteredConsumer). There is no
    "exam starting soon" reminder job, no automatic "your result is
    ready" trigger tied to Result Service actually computing a score, and
    no automatic system/maintenance announcement trigger. Today, Reminder/
    Result/System notifications can ONLY ever be sent if an Admin manually
    composes and sends one via Create Notification - they are not
    system-generated. This wasn't a bug found today, but it IS a real gap
    worth being explicit about: the notification-email fix tested all 5
    types successfully, but 3 of those 5 types are currently reachable
    only through a manual admin action, not a real product event.

(b) Student sidebar (DashboardSidebar.tsx) has no "Notification Settings"
    sub-link. The Day 39 plan called for a "Student sub-item (Notification
    Settings)" but DashboardSidebar.tsx has no submenu/children structure
    at all (unlike AdminSidebar.tsx, which does) - it's a flat list with
    a single "Notifications" -> /notifications entry. A student can only
    reach /notifications/settings by typing the URL directly or via a
    link inside the notification detail/list pages if one exists there -
    there is currently no direct sidebar navigation to it. Small, but a
    real discoverability gap.

(c) "Schedule For Later" remains store-only, as originally and honestly
    documented in ActionPlan.txt's Phase 9 scope note - no background
    dispatcher exists. A scheduled batch never triggers an email attempt,
    even after its scheduled time passes; it only becomes visible in
    in-app "mine" reads at that point. Flagged there as deliberate, still
    true today, not something that silently regressed.

(d) SMS and "Certificate Available" notification type are intentionally
    absent (not gaps) - both were explicit scope-drop decisions in
    ActionPlan.txt (no SMS credential/feature exists; no certificate
    feature exists anywhere in the app). Restating here only so this
    audit doesn't get mistaken for missing them by oversight.

(e) In-progress, not yet re-verified: adding the ExamVault logo to
    notification emails (HTML email + <img> tag). Last live test attempt
    broke the n8n workflow (HTTP 500) due to a copy-paste escaping mistake
    in the n8n UI, root cause identified (JSON-escaped text pasted
    directly into the plain expression editor). The workflow was reverted
    back to a working state (plain-text email, no logo yet) and is
    confirmed sending correctly again. The logo feature itself has not
    been successfully verified live yet - next attempt should import a
    whole corrected workflow JSON via n8n's Import feature rather than
    hand-editing individual node fields, since that has been the reliable
    method every time so far.

4. NEW FEATURE PLAN (2026-08-15): Automatic Exam Reminder
--------------------------------------------------------------------
STATUS: PLANNED - NOT IMPLEMENTED YET (design only, per plan-before-code rule)

FEATURE: close gap 2(a) above - automatically send a Reminder-type
notification (in-app + email, reusing the existing pipeline) to every
student assigned to an exam, ahead of the assignment's start time,
without any Admin having to compose it by hand.

DECISIONS CONFIRMED WITH THE USER (none derivable from existing code):
1. Timing: TWO reminders per assignment per student - one ~24 hours
   before the assignment's StartAtUtc, one ~1 hour before.
2. Recipients: everyone assigned to the assignment, regardless of
   attempt/submission status - matches how ExamAssignedEvent already
   notifies "everyone assigned" with no Submission Service check. No new
   cross-service call to Submission Service is introduced by this
   feature.
3. Job location: a new periodic background job lives inside Exam
   Service (Exam.API), not Notification Service/Worker - Exam Service
   already owns all assignment/timing data in its own DB, so no new
   cross-service HTTP call or auth flow is needed to find "assignments
   starting soon." This mirrors the existing precedent of a per-service
   background component (the Worker's consumers) rather than introducing
   a new internal-endpoint-plus-anonymous-polling pattern.

DESIGN (mirrors the existing ExamAssignedEvent / ExamAssignedConsumer
shape as closely as possible - no new architectural pattern introduced):

Exam Service side (new):
- New `ExamReminderCheckService` : BackgroundService in Exam.API (or
  Exam.Infrastructure, DI-registered from Exam.API - matches where the
  Worker's consumers live relative to Notification.Infrastructure).
  Runs on a `PeriodicTimer`, proposed interval 5 minutes (tunable later,
  not a decision that changes the design - flagged here rather than
  asked as a separate question).
- Each tick, for each of the two windows (24h, 1h) independently: query
  ExamAssignments belonging to Published exams where
  `0 < (StartAtUtc - UtcNow) <= window` (range check, not an exact
  timestamp match - robust against imprecise tick timing or occasional
  missed ticks, unlike trying to catch an exact instant).
- New small table `ExamReminderLog` (AssignmentId, UserId,
  ReminderWindow enum [TwentyFourHour, OneHour], SentAtUtc) with a
  unique constraint on (AssignmentId, UserId, ReminderWindow) - the
  idempotency guard so the same reminder is never published twice for
  the same assignment/student/window, no matter how many ticks land
  inside that window before it closes.
- For each (assignment, window) pair with at least one un-logged target:
  resolve target users via the EXISTING `IUserLookupClient.
  GetUsersByIdsAsync` (added for ExamAssignedEvent, reused as-is - no
  new client needed), insert `ExamReminderLog` rows for every target
  about to be notified (write-then-publish, so a crash after the DB
  write but before publish just skips that tick's send rather than
  double-sending - acceptable at-most-once tradeoff, consistent with
  this codebase's existing "email is best-effort" tolerance elsewhere),
  then publish one new `ExamReminderDueEvent` (`Shared.Events`) carrying
  ExamId, AssignmentId, ExamTitle, StartAtUtc, ReminderWindow, and
  `Targets: IReadOnlyList<AssignedUserInfo>` - same shape as
  ExamAssignedEvent, via Exam Service's existing RabbitMqEventPublisher
  (no new publisher plumbing needed, it already exists from Day 37).

Notification Worker side (new):
- New `ExamReminderConsumer` : BackgroundService (own queue, e.g.
  `notification-service.exam-reminder-events`) - same
  one-BackgroundService-per-event-type shape as
  UserRegisteredConsumer/ExamAssignedConsumer. Builds the message text
  based on ReminderWindow ("Your exam '{title}' starts in 24 hours" /
  "starts in 1 hour"), persists + emails via the existing
  NotificationPersistenceService (Type=Reminder, RelatedExamId set) -
  no changes needed to NotificationPersistenceService itself.

KNOWN LIMITATIONS (flagged, not engineered around - consistent with how
"Schedule For Later" store-only was flagged rather than fully solved):
- If the Exam Service process is down across an entire reminder window
  (e.g. down for 2+ hours spanning when the 1h reminder should have
  fired), that reminder is simply missed - no catch-up/backfill logic.
  Given reminders are a convenience feature, not a correctness-critical
  one, this tradeoff is accepted rather than building a more complex
  catch-up scheduler.
- No per-user reminder preference beyond the existing Notification
  Settings page's Reminder row (In-App/Email toggle) - a student who
  turns Reminder emails off simply gets no email attempt for these,
  exactly like any other type, no new preference needed.

5. IMPLEMENTATION + LIVE VERIFICATION (2026-08-15)
--------------------------------------------------------------------
STATUS: DONE

DESIGN GAP FOUND DURING IMPLEMENTATION (before any code was written):
the periodic job in Exam Service has no HTTP caller, so no JWT of any
kind - but resolving each target's email/name means calling User
Service, and the existing IUserLookupClient.GetUsersByIdsAsync forwards
a bearerToken to the [Authorize(Roles="Admin")] GET /api/users, which
this job simply doesn't have. Confirmed with the user: fixed by adding a
new anonymous, Gateway-unrouted GET /internal/users/by-ids on User
Service - same "not reachable through the Gateway, network reachability
is the boundary" pattern already established for Question Service's
Day-34 internal answer-key endpoint (see api-contracts.md precedent),
not a new auth mechanism. Only returns Email/FullName for explicitly
requested ids, never a full listing.

FILES ADDED/CHANGED:
- Shared.Events: new ExamReminderDueEvent + ReminderWindow enum
  (Exam/ExamReminderDueEvent.cs).
- User Service: IUserRepository.GetByIdsAsync + UserRepository impl;
  new Users/Internal/GetUsersByIds/ query+handler; new anonymous
  Controllers/InternalController.cs (internal/users/by-ids).
- Exam Service: new Domain.Enums.ReminderWindow + Domain.Entities.
  ExamReminderLog; ExamDbContext DbSet + unique index (AssignmentId,

VERIFICATION:
- dotnet build across the full solution: clean, zero errors.
- dotnet test across all 7 backend test projects: 196/196 passing, zero
  regressions from before this feature.
- EF migration applied against the real ExamVault.ExamDb
  (ExamReminderLogs table + unique index created).
- Live verification used REAL pre-existing data rather than a purpose-
  built throwaway, since one happened to already exist: on Exam.API
  startup, the job immediately found a real Published "Java" exam
  assignment (student "ansh") with StartAtUtc ~7.6 hours out - correctly
  matched the 24-hour window only (0 < 7.6h <= 24h), NOT the 1-hour one
  (7.6h > 1h) - proving the range-check logic classifies windows
  correctly, not just "does something."
- First attempt hit a real startup race: Exam.API's immediate first tick
  published the event before the Notification Worker's queue had
  finished binding to the fanout exchange, so that specific message was
  lost (fanout with no bound queue yet = dropped, not queued). Caught by
  checking the Worker's log showed nothing. Fixed by deleting the one
  ExamReminderLog row that tick had already written (SQL,
  DELETE ... WHERE AssignmentId=...) and restarting Exam.API - its
  do/while(PeriodicTimer) loop runs one check immediately on startup, so
  this re-triggered a clean run with the Worker fully up.
- Second attempt: full success. Exam.API log showed the DB queries,
  the internal-endpoint HTTP call (200), and "Published
  ExamReminderDueEvent for assignment ... (TwentyFourHour), 1 targets."
  The Worker's log showed ExamReminderDueEvent received -> preference
  lookup -> n8n webhook POST (200) -> Notification row inserted.
  Confirmed directly in the database: Notifications row with
  Type=Reminder, Title="Exam Reminder: Java", Message="Your exam \"Java\"
  starts in 24 hours. Please make sure you're ready to begin on time.",
  EmailStatus=Delivered.
- Idempotency confirmed structurally: the log row is written and
  SaveChanges'd BEFORE the event is published, and
  FilterUserIdsWithoutReminderLogAsync excludes already-logged
  (assignmentId, userId, window) triples - the exact mechanism that
  correctly suppressed the lost startup-race attempt from ever being
  retried blindly (it had to be cleared deliberately to re-test).
- NOT separately verified live in this pass: the 1-hour window firing
  (would need waiting for real clock time to close in on a real
  assignment, or fabricating one - not done, since the 24-hour path
  already proves the shared range-check/dedupe/publish/consume mechanism
  end-to-end and the 1-hour window uses the exact same code path with a
  different TimeSpan constant) and a student with Reminder-Email
  preference off (not re-tested here since NotificationPersistenceService
  itself - which does the per-recipient EmailEnabled check - is existing,
  unchanged code already covered by Notification.Application.Tests).
